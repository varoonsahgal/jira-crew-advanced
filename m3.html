M3.1 Two totals, one sprint

The release review is a week away. Your delivery lead pastes two numbers into the review notes for Alerts Squad's last closed sprint, ALR-2026.q4.3. One comes from the native Jira Sprint Report on the ALR - Sprint Execution board ↗. The other comes from a sample eazyBI report that leadership reads.

Jira Sprint Report and Velocity · board 6219story points completed (5 work items)
≠
Sample eazyBI measure · "Sprint story points completed"11story points completed (3 work items)

Nobody typed a wrong number. Both tools counted correctly against their own rules. The trouble is that a release decision will quote one of them as "what Alerts Squad delivered", and the two numbers answer different questions. Your job in this module is to name each question, prove the gap with Jira keys, and write down the definition so the next reader doesn't have to repeat your investigation.

Don't average, don't pick the bigger oneA number you can't define is an opinion. If you can't say which statuses count as "completed", at which moment, for which team and from which data load, don't put the number in a decision yet. Record it as unverified and keep investigating.

M3.2 Measures need definitions

eazyBI reports are built from measures (numbers such as "Sprint story points completed") sliced by dimensions (Sprint, Team, Issue Type, Status and others). A sprint measure is only meaningful when you know three things: which items belong to the sprint, what counts as completed, and at what moment the status is read.

Measure (eazyBI naming)What it countsWatch out for
Sprint issues committed / Sprint story points committedItems (or points) in the sprint when it started.Re-estimates after the start don't change commitment. Compare with the Velocity report's Commitment bar.
Sprint issues addedItems pulled in after the start.CRW-21 in SWP-2026.q4.2 is the classic case: a 3-point Bug added after start and completed, so completed matched commitment with different work.
Sprint issues completed / Sprint story points completedItems (or points) counted as done for the sprint."Done" needs a definition: a board column, a status category, a resolution, and a moment (close or now).

Three completion definitions you will meet

A · Board completion

What Jira's Sprint Report and Velocity chart use: the item sat in the board's rightmost column when the sprint closed. The board's column mapping decides which statuses that includes.

B · Done category at close

The course's sample eazyBI definition: the item's status was in the Done status category at sprint close. Ready for Release is not in that category, so it doesn't count.

C · Done category now

A current-state count: is the item Done at the last data import? It drifts every time work moves after the sprint, and it depends on when the data was loaded.

The ALR board is the reason definition A and definition B disagree. Alerts Squad maps Ready for Release into its Done column. Swap Squad doesn't. Same workflow, same project, different board configuration.

Golden Template diagnosisBoard-column mapping is one of the four things the template helps you diagnose (fields, statuses, parent links, board filters and columns). A team-to-team mapping difference isn't automatically wrong, but it must be a decision someone owns. "Is Ready for Release delivered or done?" is exactly the Delivered/Done and release-mapping question the template owner has to confirm.

Because SWP's rightmost column only holds Done, definitions A and B give the same SWP numbers (21, 18 and 16 for q4.1–q4.3, average 18.33). Comparing SWP's velocity with ALR's board velocity therefore compares two different definitions. That is the most common way team-to-team charts mislead a leadership audience.

M3.3 Align scope and import time before you compare

Before you blame a definition, make sure the two views look at the same slice of data. Four alignment checks catch most false discrepancies:

CheckJira sideeazyBI sideTypical trap
TeamThe board's filter (board 62 filters on the Alerts Squad team id).Team dimension member "Alerts Squad".The Team field wasn't selected in the import options, so the Team dimension has nothing to filter on and the report is empty or all teams together.
SprintSprint ALR-2026.q4.3 (id 50).Sprint dimension member ALR-2026.q4.3.Similar names across teams, or a report defaulting to the current sprint.
Filter and estimateBoard estimation statistic: Story Points.Story Points imported as a measure.Story Points not imported, so the report falls back to issue counts.
Import timeLive: Jira reads current data."Last import" time on the account.The report reads a data load from before an item moved. Current-state measures drift with each import.

The Team field deserves its own warning. In JQL, a team name looks like it should work, but it doesn't:

project = CRW AND Team = b5cf2b12-d7a8-49e4-bf33-0da3acadf620 AND sprint = "ALR-2026.q4.3"
Import time is part of the numberEvery eazyBI account shows when its data was last imported. Write that time next to any number you quote. A close-time measure (definition B) stops changing once the sprint is closed and imported. A current-state measure (definition C) changes whenever someone moves an item after the sprint. If two people quote different numbers from "the same report", ask for both import times first.
Report copies, not report editsDon't change a shared report to make it match your view. Save a copy, put the definition in the copy's description (measure, completion rule, moment, team, sprint, source board, import time), and share the copy. If the shared report's definition is wrong, that is a change request for its owner, not a silent edit.

M3.4 Trace the gap to the item

A discrepancy is only explained when you can name the work items that make up the difference and show the status evidence for each. Three tools do the tracing:

  1. Drill through the eazyBI measure to the list of issues it counted. In eazyBI, use "Drill through issue" on the cell.
  2. Compare that list with the Sprint Report's Completed Issues. The keys that appear in only one list are the gap.
  3. Prove the status with history: the Sprint Report shows status at close; the work item's History tab shows when it changed; JQL history operators confirm it across items.
project = CRW AND sprint = "ALR-2026.q4.3" AND status WAS "Ready for Release"
project = CRW AND sprint = "ALR-2026.q4.3" AND statusCategory = Done ORDER BY key ASC

The first query is history-based and returns both gap items. The second is current-state. It should return four items today, because CRW-55 was released after the sprint closed and CRW-54 is still in Ready for Release. Neither JQL result reproduces the board's 19 or the measure's 11 on its own. That's the point: current-state JQL can't tell you what was true at sprint close. The Sprint Report and history can.

    Debrief: what a strong answer looks like

    Totals and scope. Board 62 Sprint Report and Velocity: 19 points, 5 items completed. Sample eazyBI measure "Sprint story points completed" (Done status category at sprint close): 11 points, 3 items. Both are for Team = Alerts Squad (Team field imported, filtered by team), sprint ALR-2026.q4.3 (id 50), estimate field Story Points, latest import.

    Reason. The ALR board maps Ready for Release into its Done column, and the Velocity and Sprint Report count whatever sat in the rightmost column at close. The sample measure only counts the Done status category. CRW-54 (5) and CRW-55 (3) were in Ready for Release at close: 19 − 11 = 8.

    Source keys. CRW-54: Ready for Release at close and still today. CRW-55: Ready for Release at close, Done today (released after the sprint). status WAS "Ready for Release" returns both.

    Definition. For example: "Sprint story points completed = sum of Story Points of items in the sprint at close whose status category was Done at close. Team = Alerts Squad (Atlassian Teams field, imported). Sprint ALR-2026.q4.3, source board ALR - Sprint Execution (62). Import: latest. Ready for Release is not counted."

    Import-time angle. A current-state version reads 11 before CRW-55 reached Done and 14 after. Close-time measures stop moving once the sprint is closed and imported; current-state measures never stop moving.

    Owner action. The template owner, with Alerts Squad's product owner, confirms whether Ready for Release counts as done for ALR (the Delivered/Done and release-mapping decision). Until then, the release review quotes both numbers with their definitions: "19 points reached ALR's Done column, of which 11 points were released at close." The reporting author adds the definition to the shared report's description through its owner. Note that CRW-54 is still not released; in Module 4 you'll find that one of its acceptance criteria has no executed test.

    Checkpoint

    1. Jira says 19 completed points, eazyBI says 11, for what looks like the same sprint. What do you do first?

    Most discrepancies are scope or timing mismatches. Once scope is aligned, the remaining gap comes from the definitions, and you explain it with keys. Re-importing can't fix a definition difference, and an average describes nothing.

    2. Why does the ALR Velocity report count CRW-54 as completed while it's still in Ready for Release?

    The board's column mapping decides. If Ready for Release were in the Done category, the sample eazyBI measure would count it too, and it doesn't. SWP's board keeps Ready for Release in its own column, so the same status doesn't count there.

    3. A current-state measure for ALR-2026.q4.3 shows 11 in one person's report and 14 in another's. Same report definition. Most likely cause?

    Current state moves with every import. CRW-55 was released after the sprint closed. That's why you write the import time next to the number. CRW-21 belongs to a SWP sprint, and a team-name filter would give 0, not 11.

    4. Your eazyBI report filtered to Team = Alerts Squad shows no data at all. What's the best first check?

    Custom fields such as Team and Story Points only appear in eazyBI when they're imported. It's the reporting cousin of Team = "Swap Squad" returning nothing in JQL: no error, just silence.

    5. Which note is fit to sit next to the number in a release decision?

    A reusable note names the measure, the rule, the moment, the scope, the import and the keys behind any difference. The others are claims nobody can check.
